# phis (phi server)

`phis` is the central server of a Phi installation. It owns the PostgreSQL schema `phis`, the Site
configuration, CMS drafts and publication state, global users and Site sessions, Media Spaces and
Storage Profiles, translations, and the installed server Add-ons. Sites are separate Next.js
applications that render with `@phis/ui` and reach `phis` from their own server; a browser never calls
`phis` directly.

`phis` is itself a Next.js application (`output: "standalone"`). Almost everything it answers is an HTTP
API; the only pages it renders are the operator pages described under [Operator UI](#operator-ui).

## How a Site reaches phis

- A Site runtime forwards browser traffic through its own same-origin route handlers, generated by
  `phis init` / `phis reconcile` ([docs/CLI.md](./docs/CLI.md#init-reconcile-update-site-scaffold)):
  - `/api/auth/*` to `/api/v1/auth/*`
  - `/api/site/*` to `/api/site/*`
  - `/api/addons/*` to `/api/v1/addons/*`
  - `/api/hooks/*` to `/api/v1/hooks/*`, without the Site token
  - `/api/site/forms` through the Form gateway
- Server-rendered reads call `/api/v1/site`, `/api/v1/site/area`, `/api/v1/site/page` and the other
  `/api/v1/*` reads directly with the Site token.
- `/api/v1/*` guards read the token from `x-phis-token`, or from `Authorization: Bearer <token>` when
  that header is absent; the Site runtime sends the Bearer form. `api.internalToken` has internal scope;
  `api.publicToken`, when set, is accepted where a route does not require internal scope. Requests
  without internal scope are rate limited unless `api.disableRateLimit` is `true`. See
  `src/lib/api-v1-guard.ts`.
- Site-scoped endpoints require `x-phis-site-key`. A request without it is not Site-scoped.
- No route emits `Access-Control-Allow-*`; browser traffic stays same-origin to the Site.
- Session state and CSRF validation are owned by `phis`; the Site sets and reads the browser cookies.
- The Site's route graph (`src/app/(site)/{area}`, the Public `(site)/[root]` tree, and the static
  rendering tree) is specified in
  [phis-ui NEXT_INTEGRATION.md](../phis-ui/NEXT_INTEGRATION.md).
- CMS Areas are `public`, `app`, `admin`, `builder`, `editor`, and `accounting`
  (`src/lib/constants/cms-areas.ts`). Which roles reach which Area is defined in
  [AUTHORIZATION.md](./AUTHORIZATION.md).

Every route handler, with the access it checks, is listed in the generated
[HTTP API reference](./docs/API.md).

## Requirements

- Node.js `>=24.21.0` for the server, the emitted CLI (`dist/phis.mjs`), development and every Site.
  Earlier releases hold on to finished React Flight renders and run out of memory under load. The source CLI (`pnpm phis`) runs TypeScript through
  `--experimental-strip-types`.
- PostgreSQL. The schema is `scripts/sql/001_create_phis.pgsql`, applied by `phis schema apply` or by
  the setup pages.
- Next.js 16 (`next` is a dependency of this package).
- In the workspace, pnpm with the workspace root `pnpm-lock.yaml`.

## Configuration

### Runtime configuration files

The installation root is `PHIS_ROOT`. Without it the server uses `/srv/phis/stages/prod` in production
and the application directory otherwise; the CLI uses the current working directory and accepts
`--root|-r <path>`. Under that root:

| File | Tracked | Content |
| --- | --- | --- |
| `config/phis-config.json` | yes | Versioned, non-secret defaults. |
| `config/phis-runtime.json` | no | Local values and secrets for this installation; overrides `phis-config.json`. |
| `config/phis-addons.json` | no | Installed Add-ons and their desired global state, written by `phis addon`. |
| `config/phis-modules.json` | no | Site Module packages, written by `phis module`. |
| `config/phis-instance.json` | no | The phis version that last operated this root. |

The effective configuration is the code default (`DEFAULT_CONFIG` in `src/lib/config-core.ts`), then
`phis-config.json`, then `phis-runtime.json`. `config/phis-runtime.example.json` shows the shape.
The three files the CLI writes are deployment state, not source: what is installed on one machine is
not a property of the repository, so they are untracked and an absent one reads as empty. The
`.example.json` beside each shows what a fresh root starts from.
`phis config validate` checks the merged result.

| Key | Meaning |
| --- | --- |
| `database.uri` | Connection of the serving role: the running server, and `phis schema check`/`apply` for the Core schema. |
| `database.migrationUri` | Connection of the migration role, which owns Add-on schemas: `phis addon migrate`, `phis addon purge`, `phis schema drop`. There is no fallback to `database.uri`. |
| `api.internalToken` | Token with internal scope, used by Site runtimes. The setup pages generate one. |
| `api.publicToken` | Optional token without internal scope. |
| `api.phisCdnPublicToken` | Token this installation sends when it reads global translations from `translation.cdnBaseUrl`. |
| `api.disableRateLimit` | Turns off the per-address rate limit of `/api/v1/*`. |
| `secrets.encryptionKey` | 64 hex characters. Key for the encrypted secret store `phis.server_secrets`; an instance without it does not report ready. `phis secret init-key` writes it. |
| `secrets.encryptionKeyVersion` | Positive integer version of that key. |
| `auth.transactionEncryptionKey` | 64 hex characters. Encrypts authentication transaction state. |
| `registration.intentEncryptionKey` | 64 hex characters. Encrypts the password held by a pending registration intent. |
| `deepl.apiKey`, `deepl.apiUrl` | DeepL access when `translation.mode` is `deepl`. |
| `translation.mode` | `deepl`, `cdn`, `custom`, or `none`. |
| `translation.sourceLocale` | Installation fallback for a Site source locale. |
| `translation.supportedLocales` | Locales the installation offers. `translation.allowedLocales` is read when `supportedLocales` is absent. |
| `translation.cdnBaseUrl`, `translation.customEndpoint` | Upstream for the `cdn` and `custom` modes. |
| `translation.allowPublicReads`, `translation.allowPublicWrites` | Whether a public-token request may read from `/api/v1/tr` and `/api/v1/locales`, and whether it may write translations through `/api/v1/tr`. |
| `platformSuperUsers` | Platform operators, written by `phis operator`. |
| `bootstrap.enabled` | Serves the setup pages; completing setup sets it to `false`. |
| `runtime.containerized` | The operator overview reports the deployment as a container. Default `false`. |
| `forms.timeouts.minSubmitMs`, `forms.timeouts.maxSubmitMs` | Minimum and maximum submit age for form guard checks. |
| `email.from`, `email.fromName` | Default sender. |
| `email.smtp.targets`, `.secure`, `.ignoreTls`, `.tlsRejectUnauthorized` | Outbound relays (`host:port`), tried in order. |
| `media.storageKeyPrefix`, `media.local.rootDir` | Seed of a Site's Local Storage Profile; the root defaults to `<PHIS_APP_ROOT>/storage/media`. Storage Providers bind per Site in `media_storage_profiles` ([GROUPS_AND_STORAGE.md](./GROUPS_AND_STORAGE.md)). |
| `media.defaults.userQuotaBytes`, `media.defaults.groupQuotaBytes` | Applied once when a Site's `site_media_config` row is materialized. |
| `sites.sourcePathRoot`, `sites.instancePathRoot`, `sites.basePort` | Defaults for Site source and instance locations used by `phis site config`. |
| `sites.overrides.<siteKey>.sourceLocale` | The immutable Site source locale, written by `phis site add`. |
| `sites.overrides.<siteKey>.source`, `.instances` | `host`, `port`, `path` of the Site source and its instances, written by `phis site config`. |

Other secrets -- authentication provider secrets, Storage Profile credentials, Add-on secrets -- live
encrypted in `phis.server_secrets` and are managed with `phis secret`, so every instance of an
installation reads the same values.

The server caches the merged configuration for up to four hours. The operator and setup pages reset
that cache when they write `phis-runtime.json`; a change made to the files by hand takes effect on
restart or when the cache expires.

### Environment variables

| Variable | Meaning |
| --- | --- |
| `PORT` | Port the runtime listens on. |
| `HOSTNAME` | Interface the standalone server binds. `next dev` ignores it and takes `-H`. |
| `PHIS_ROOT` | Installation root (see above). Add-on artifacts live under `<PHIS_ROOT>/addons`. |
| `PHIS_APP_ROOT` | Application directory: where `scripts/sql` is read from, the default Local media root, and the development configuration root. Defaults to the directory derived from the running code; the `phis` wrapper and the Debian unit set it. |
| `TRUST_PROXY` | Number of our reverse proxies in front of the process. |
| `PHIS_INSTANCE_ID` | Name of this process in `phis.server_instances`. Defaults to host name and root. |
| `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` | Base64 of 32 bytes. Required in production; identical across the instances of one installation. The Debian package generates one per stage. |
| `PHIS_ADMIN_LOG_JOURNAL_UNITS` | Comma-separated systemd units the Site log feed reads from the journal. |
| `PHIS_SKIP_VERSION_CHECK` | Lets the CLI operate a root last operated by a newer phis. |
| `PHIS_PG_TEST` | `1` enables the PostgreSQL integration tests (`pnpm test:pg`). |

The Debian unit and stage environment files set `HOSTNAME=127.0.0.1`, and so does the Site runtime unit
from `phis site config systemd`: the reverse proxy is the intended entry point, and a runtime bound to
`0.0.0.0` also answers callers who write `X-Forwarded-For` themselves. The `docker-compose` profile keeps
`0.0.0.0` and relies on `expose`.

`TRUST_PROXY` follows the Express convention: unset or `true` is one proxy, `false` or `0` is none, a
number is that many. The client address is counted from the right of `X-Forwarded-For`, skipping our own
hops; with no trusted proxy nothing is read from the headers. `readPhiClientIp`
(`src/lib/helpers/request.ts`) answers it for the rate limit, the address recorded at login, and the form
abuse log.

- Behind the shipped nginx profile: `true`.
- Behind a CDN in front of that nginx: `2`.
- Behind no proxy: `0`.

`PHIS_RELEASE_ID` is not an environment input: `next.config.ts` bakes the package version into the build,
and capability responses report it ([SERVER_ADDONS.md](./SERVER_ADDONS.md)).

## Running

```bash
pnpm dev          # next dev
pnpm build        # next build (standalone output)
pnpm start        # next start
pnpm test         # vitest
pnpm test:pg      # PostgreSQL integration tests
```

A production stage runs the standalone `server.js` with `PHIS_ROOT=/srv/phis/stages/<stage>`; the Debian
package ships `phis@.service` for that. Loopback ports conventionally start at `5301` for the first
stage and count up; the stage name does not determine the port.

The package's proxy templates (`debian/phis.nginx.conf`, `debian/phis.apache2.conf`) put the instances
of one stage in a pool — `upstream phis` with `keepalive 64` and `keepalive_timeout 4s`, or a
`balancer://phis` with `ttl=4` — because a pooled connection held longer than Node's 5 s keep-alive
timeout answers a `POST` with `502` ([README.Debian](./debian/README.Debian), phis-host `README.md`).
A second stage is a second installation and gets its own pool and server block.

`src/instrumentation.ts` starts the instance heartbeat into `phis.server_instances` and, in production,
refuses to start without a valid `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`.

### Logs

Runtime logs are one-line JSON objects on stdout/stderr for journald; there is no log table. The service
names (`phis`, `ui`, `site`, `cli`), the record fields, and the logger interface are defined in
`@phis/contracts/logging`. `GET /api/site/admin/logs` reads the journal for the units in
`PHIS_ADMIN_LOG_JOURNAL_UNITS` and filters by `siteKey`. Passwords, tokens and secret material are never
logged. CLI commands print human-readable text, or JSON with `--json`.

## Operator UI

| Path | Purpose |
| --- | --- |
| `/setup` | First setup: runtime check, platform operator, translations, database, schema, first Sites. Served only while `bootstrap.enabled` is `true`; otherwise `404`. |
| `/operator/login`, `/operator` | Operator session and control plane: overview, Sites, translations, operators, infrastructure. |
| `/recovery` | Shown to a signed-in operator while the database is unreachable. |

Operators are `platformSuperUsers` in `config/phis-runtime.json`; they are not Site users.

## CLI

`phis` is the operator CLI: runtime configuration and validation, Sites and their deployment profiles
(nginx, Apache, systemd, docker-compose), platform operators, Site admins, secrets, schema, Storage
Profiles, Site Modules, Add-ons, instances, and maintenance tasks. It runs against `PHIS_ROOT` or the
current working directory, or `--root|-r <path>`, and prints JSON with `--json|-j`. `./phis` in the
repository runs `dist/phis.mjs` when built (`pnpm build:cli`) and the TypeScript source otherwise;
`scripts/install-phis-cli.sh` links it into the system path. `phis` without arguments prints the usage.

The command reference is [docs/CLI.md](./docs/CLI.md); installing a stage is described in
[docs/INSTALL.md](./docs/INSTALL.md).

## Add-ons

Server extensions are Add-ons, Site extensions are Modules. One package carries one product with a Module
half, an Add-on half, or both. Add-on artifacts are installed at runtime into `<PHIS_ROOT>/addons` with
`phis addon install` and recorded in `config/phis-addons.json`; no Add-on is compiled into `phis`. Only
the CLI installs, migrates, or globally enables Add-on code; a Site enables an installed Add-on for
itself. How to build one is in [ADDON_HOWTO.md](./ADDON_HOWTO.md), the server contract in
[SERVER_ADDONS.md](./SERVER_ADDONS.md).
